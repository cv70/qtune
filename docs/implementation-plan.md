# Qtune 实施计划

本文档用于把 `Qtune 光影音乐工作站` 的产品定义转化为可执行的交付阶段，确保硬件设备、配套 App 和内容平台按照统一节奏推进，而不是分别扩张。

## 1. 实施原则

- 先统一产品边界，再进入具体方案细化
- 先打通核心体验闭环，再扩展平台能力
- 先保证设备、App 和平台的概念一致，再优化局部细节
- 先做可验证的最小体验，再做更大范围的内容和生态投入

## 2. 阶段划分

建议按六个阶段推进：

1. 产品定义与规格冻结
2. 系统与硬件方案细化
3. App 信息架构与核心交互定义
4. 平台内容模型与分发链路定义
5. 集成体验验证
6. 上线准备与后续版本规划

## 3. 阶段一：产品定义与规格冻结

目标：

- 明确 `Qtune v1.0` 的产品边界、用户价值和功能范围

任务：

- 冻结产品定位和用户画像
- 冻结核心模式定义
- 明确硬件、App 和平台的首版范围
- 建立统一术语表和文档导航

完成标准：

- 产品文档结构稳定
- `v1.0` 范围清晰
- 跨文档术语一致

## 4. 阶段二：系统与硬件方案细化

目标：

- 将产品需求转化为系统边界和硬件设计约束

任务：

- 明确设备端、App 端、云端、平台端边界
- 细化投影、感应、音频、连接、电源与结构约束
- 定义校准、演奏和配置同步主链路
- 识别关键技术风险与验证项

完成标准：

- 系统架构可支撑核心用例
- 硬件架构具备清晰模块边界
- 技术风险可被验证和管理

## 5. 阶段三：App 信息架构与核心交互定义

目标：

- 建立 App 在 `v1.0` 中的核心使用路径

任务：

- 明确设备中心、模式中心、编辑器、录制和内容入口的边界
- 定义 `光影钢琴`、`音乐画布`、`节奏冒险` 的入口和关系
- 设计模板编辑、录制发布和内容同步流程
- 明确账户体系与本地草稿策略

完成标准：

- App 主流程完整
- 模板编辑和录制分享链路清晰
- 关键数据对象已定义

## 6. 阶段四：平台内容模型与分发链路定义

目标：

- 建立平台基础内容闭环，为 `v1.0` 分享能力提供支撑

任务：

- 定义模板、谱面、作品和创作者资料模型
- 规划推荐流、搜索、专题和活动能力边界
- 明确审核、治理和后台运营的最小能力
- 规划平台与 App 的同步边界

完成标准：

- 平台核心对象清晰
- 内容分发和社区互动闭环成立
- `v1.0` 不做的能力已经明确排除

## 7. 阶段五：集成体验验证

目标：

- 从完整产品链路角度验证 Qtune 是否具备可交付体验

任务：

- 走通校准、演奏、录制、分享、模板复用等核心链路
- 验证设备与 App 的连接稳定性
- 验证模板和作品的同步路径
- 评估典型场景中的可用性风险

完成标准：

- 核心使用场景可被连续走通
- 关键交互链路无明显断点
- 首版风险列表得到更新

## 8. 阶段六：上线准备与后续版本规划

目标：

- 为 `v1.0` 对外呈现和后续演进建立基础

任务：

- 完善路线图和版本范围说明
- 准备首批模板、谱面和官方内容
- 梳理后续版本的技术储备方向
- 明确配件、创作者合作和运营启动需求

完成标准：

- `v1.0` 对外口径清晰
- 冷启动内容有基础支撑
- `v1.5` 与 `v2.0` 的方向得到约束

## 9. 验证清单

每个阶段完成前，至少验证以下问题：

### 9.1 产品一致性

- 是否仍然只使用 `Qtune` 命名
- 是否存在旧原型术语残留
- 是否能用一句话说明当前版本做什么、不做什么

### 9.2 系统一致性

- 设备、App 和平台的职责是否清楚
- 是否存在同一能力被多个文档重复定义

### 9.3 体验一致性

- 校准、演奏、编辑、录制、分享是否形成闭环
- 关键概念在设备端和 App 端是否同名

### 9.4 版本一致性

- `V1.0`、`V1.5`、`V2.0` 的边界是否清晰
- 后续能力是否错误地挤入首版要求

## 10. 推荐推进顺序

1. 完成产品定义和文档重构
2. 固化系统和硬件架构
3. 固化 App 架构
4. 固化平台架构
5. 验证完整体验链路
6. 进入更具体的原型与交付规划
